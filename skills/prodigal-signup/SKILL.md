# Prodigal Signup

가입 과정만 다루는 재사용 스킬이다. 색, 폰트, 로고는 프로젝트의 것을 그대로 쓰고, 이 스킬에서 정하지 않는다.

이름은 돌아온 탕아에서 왔다. **떠난 사람을 다시 심사하지 않는다. 단, 본인임이 확인된 뒤에 알아본다.** 모든 판단의 기준은 이 문장이다.

## 흐름

1. 입력 파악 → 2. 화자 정하기 → 3. 가입 상태 흐름 설계 → 4. 이메일 코드 연결 → 5. 검증 → 6. 보고

### 1. 입력 파악

프로젝트에서 먼저 찾고, 없는 것만 묻는다.

| 항목 | 기본값 |
|---|---|
| 인증 서비스 | Supabase Auth |
| 가입 방식 | 이메일 코드 인증 후 프로필 입력 |
| 탈퇴 후 복귀 | 탈퇴 시 본인이 선택, 기본은 완전 삭제 |
| 캡차 | 없음. 호출 제한으로 대응하고, 요청이 있을 때만 추가 |
| 추천인 코드 | 없음. 요청이 있을 때만 추가 |

### 2. 화자 정하기

문구를 쓰기 전에 "이 서비스에서 누가 말하는가"를 먼저 정한다. 화자 없이 쓰면 어느 서비스에나 붙는 무난한 해요체가 되고, 서비스의 개성이 사라지기 때문이다.

- 화자는 서비스의 세계에서 찾는다. 예: 게임의 문지기, 도서관의 사서, 헬스장의 코치.
- 화자의 대사와 입력칸 안내를 분리한다. 대사는 분위기를 맡고, 입력칸 아래의 건조한 문장은 고칠 방법을 맡는다. 오류까지 캐릭터 말투로 쓰면 무엇을 고쳐야 할지 흐려진다.
- 말투는 한 가지로 통일하고, 상황별 대사표를 먼저 쓴 뒤 화면에 넣는다.

### 3. 가입 상태 흐름

이메일 인증이 끝나기 전에는 모든 사람에게 같은 화면을 보여 준다. 인증 뒤에 아래처럼 나눈다.

| 인증 뒤 상태 | 이동 |
|---|---|
| 처음 온 이메일 | 프로필 입력 |
| 활동 중인 계정 | 바로 입장 |
| 휴면 계정 | 마지막 접속일로 알아보고 입장 |
| 세이브가 있는 탈퇴 유저 | 기록 복원, 새 비밀번호만 입력 |
| 세이브가 없거나 만료된 탈퇴 유저 | 처음 온 이메일과 동일 |

지켜야 할 것과 이유:

- **가입 여부를 인증 전에 드러내지 않는다.** 이메일만 넣어 보고 다른 사람의 가입 사실이나 옛 닉네임을 알 수 있으면 개인정보 노출이다. 코드 요청 응답도 이메일과 상관없이 같아야 한다.
- **비밀번호는 항상 가려진 상태로 시작한다.** 보기 토글은 칸마다 두고, 화면을 벗어나면 다시 가린다.
- **동의 항목은 하나로 묶지 않는다.** 연령, 약관, 개인정보를 각각 체크하게 하고 미리 체크해 두지 않는다. 국내 서비스의 연령 기준은 만 14세로 두고 법령 원문을 확인한다.
- **오류는 입력을 마친 뒤에 보여 준다.** 타이핑 도중에 빨간 글자가 뜨면 사용자를 재촉하게 된다.
- **돌아온 유저에게 입력을 다시 받지 않는다.** 복원할 수 있는 것은 복원하고, 다시 받아야 하는 비밀번호만 묻는다.

복귀 보상을 쓰는 서비스라면 기간을 나눈다. 예: 30일 이내 100%, 31~90일 포인트 50%와 진행 중인 혜택, 90일 초과 파기. 포인트와 혜택 복원은 이메일당 1회로 제한해 탈퇴와 복귀를 반복하는 악용을 막는다. 탈퇴 후 보관은 별도 동의와 기간 제한을 전제로 설계하고, 실서비스 전 개인정보보호위원회 자료를 확인하라고 보고에 적는다.

> DB 스키마와 Edge Function 템플릿은 아직 이 스킬에 없다. 지금은 이메일 코드 모듈까지 제공한다.

### 4. 이메일 코드 연결

`references/email-otp.md`를 읽고 순서대로 진행한다. 코드 메일은 Supabase 대시보드 설정이 빠지면 조용히 링크 메일로 나가거나 시간당 몇 통 뒤에 막히므로, 코드보다 설정 확인이 먼저다. 무료 플랜은 외부 메일 서버를 연결해야 템플릿을 바꿀 수 있으니 SMTP부터 연결한다.

- 앱 코드: `templates/email-code.mjs`를 복사해 쓴다. 발송, 검증, 재발송 대기, 오류 분류가 들어 있다.
- 메일 본문: `templates/email-code-mail.html`을 2단계의 화자 말투로 고쳐 Confirm signup과 Magic Link 두 템플릿에 넣는다.
- 발송 시험: `node scripts/send_test_code.mjs <URL> <공개 키> <받는 이메일>`

계정 생성, 결제, 비밀번호 입력은 사용자가 직접 한다. 비공개 키(`service_role`, `sb_secret_`)는 프론트엔드와 저장소에 넣지 않는다.

### 5. 검증

- 처음 쓰는 이메일과 이미 인증된 이메일 양쪽으로 받아 봐서, 둘 다 링크가 아니라 코드가 오는지 본다. 스팸함도 확인한다.
- 메일의 코드 자릿수가 입력칸과 같은지 본다.
- 틀린 코드, 재발송 대기, 발송 한도 초과 때 화면이 어떻게 보이는지 본다.
- 가입된 이메일과 처음 온 이메일의 화면과 문구가 같은지 비교한다.

### 6. 보고

무엇을 실제 메일로 확인했고 무엇을 확인하지 못했는지 나눠서 적는다. 사용자가 해야 할 대시보드 설정이 남았으면 목록으로 적는다.
